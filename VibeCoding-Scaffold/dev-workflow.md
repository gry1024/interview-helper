# Vibe Coding 开发流程与规范

> 单人 + AI 协作开发的总规范：怎么立项、怎么迭代、每次怎么验收。
> 前端样式规范见 [frontend-design-system.md](./frontend-design-system.md)。

---

## 1. 核心原则

1. **AGENT.md 是 AI 的入职手册** — 项目根目录放一份，AI 每次新会话第一件事读它。写得越清楚，AI 越不翻车。
2. **先 MVP，后完美** — 核心闭环跑通前，不碰用户体系、订阅、界面美化。
3. **spec 先于代码** — 预计超过 30 分钟的功能，先写 spec 再让 AI 动手。
4. **每次迭代走 checklist** — 不因为改动小就跳过验证。
5. **安全 > 稳定 > 体验 > 新功能**。

---

## 2. 项目三阶段

### 阶段一：立项

一段话讲清三件事，结束标志是能向陌生人一句话说清"这个产品是干嘛的"：

- **谁会来用、来做什么**
- **为什么比现有方案好**
- **核心闭环**（砍到不能再砍的一条数据流）

同时明确写出**不做的事**——这能防止 AI 画蛇添足。

### 阶段二：本地 MVP

**不碰服务器。**

- [ ] 项目骨架 + git init
- [ ] 写 AGENT.md（用第 3 章模板）
- [ ] 数据层跑通"获取 → 存库"
- [ ] 后端 API 一个 endpoint 一个 endpoint 测，不要一次写完
- [ ] 前端能展示真实数据即可，**不做美化**
- [ ] 核心闭环在本地跑通

### 阶段三：迭代循环

之后所有工作（新功能 / 修复 / 重构）都走第 4 章的迭代流程。

## 3. AGENT.md 模板

复制到项目根目录，替换 `[...]`。**不进 GitHub**（含服务器路径等敏感信息，`.gitignore` 写上 `AGENT.md`）。

```markdown
# AGENT.md — [项目名称]

## 一句话定义
[谁会来用、做什么、解决什么问题]

## 技术栈
| 层 | 选型 |
|----|------|
| 后端 | [...] |
| 数据库 | [...] |
| 前端 | [...] |

## 目录结构
[每个目录的用途]

## 代码规范
- 文件命名 [kebab-case]，数据库表 [snake_case 复数]，路由 `/api/...`
- 所有密钥走 .env，代码只读环境变量，绝不硬编码
- SQL 全部参数化，禁止字符串拼接
- 用户输入去控制字符；渲染用户内容必须 XSS 过滤
- API 必须限流；管理员鉴权 fail-closed（密码为空 → 一律拒绝）

## 已知限制与坑
- [踩坑 1：...]
- [踩坑 2：...]

## 部署
- 服务器 [IP / SSH 别名]，部署命令让 AI 按技术栈生成
```

## 4. 单次迭代流程（核心）

每次功能 / 修复 / AI 任务，按 A → F 走一遍。

### A. 动手前

- [ ] 一句话说清要做什么
- [ ] 明确范围：涉及哪些文件 / 表
- [ ] 明确不做的事
- [ ] 超过 30 分钟的功能：写 spec（第 5 章模板）
- [ ] 动 schema 先备份数据库

### B. 跟 AI 沟通

实际协作就是口头几句话，想到哪说到哪，**不需要固定指令格式**。说清"要做什么、期望什么样"即可，AI 会自己读代码理解上下文。

两句口头提醒值得养成习惯：

- 改动范围小时顺口加一句"**只改这一处，别动别的**"——AI 天然倾向于顺手多改
- 讨论来回超过几个回合的复杂功能，把结论沉淀成 spec（第 5 章）再让 AI 照着做，防止长对话后遗忘

规范不靠说话方式维持，靠后面的 C（git diff）和 D（本地验证）兜底。

### C. AI 实现后 Review

- [ ] `git diff` 看实际改动（不要只信 AI 的描述）
- [ ] 没改没让它改的代码
- [ ] 没有硬编码密钥 / IP / 域名
- [ ] 数据库查询全部参数化

### D. 本地验证

- [ ] 主路径跑通：点击 → API → 落库 → 反馈
- [ ] 边界：空 / 超长 / 特殊字符 / 网络断开
- [ ] 回归：之前的功能没被破坏
- [ ] 桌面（>1024）/ 平板（640-1024）/ 手机（<640）布局正常

### E. 提交推送

```bash
git status            # 看改了哪些
git add [具体文件]    # 不用 git add .，防误加密钥
git commit -m "..."   # 写"为什么"，不写"做了什么"
```

### F. 部署与文档同步

- 部署哲学（永远不变）：**推代码 → 重启服务 → 验证 → 监控 24h**。具体命令让 AI 按当前技术栈生成，不背命令。
- [ ] 更新 AGENT.md（新依赖 / 新路由 / 新坑）
- [ ] 更新 README（用户视角的变化）

## 5. Spec 模板

**何时写 spec**：

| 改动类型 | 是否需要 |
|----------|----------|
| 新功能模块 / 新页面 | **必须** |
| 改核心 API 协议 / 加表 | **必须** |
| 重构某模块 | 强烈建议 |
| 改 UI 细节 / 修明确小 bug | 不需要 |

复制到 `docs/specs/YYYY-MM-DD-<feature>.md`：

```markdown
# [功能名] 设计文档

> 目标：[一句话说清解决什么问题]

## 背景
[系统现状、缺什么、痛点]

## 数据库改造（如有）
[SQL + 老数据兼容性说明]

## API 设计（如有）
| 端点 | 方法 | 鉴权 | 说明 |
|------|------|------|------|

## 前端设计（如有）
[入口位置 / UI 结构 / 关键交互状态]

## 安全考虑
- [ ] 鉴权级别 / 限流 / 输入过滤 / XSS

## 改动清单
| 文件 | 改动 | 风险 |
|------|------|------|

## 验收标准
- [ ] [curl / 浏览器可验证的项]

## 实现顺序（给 AI）
1. 数据库 → 2. 后端 → 3. 前端 → 4. 测试 → 5. 文档

## 反模式（明确不要做）
- 不要重构 [xxx]
```

**spec 写完贴给 AI 的话**：

```markdown
请阅读 docs/specs/YYYY-MM-DD-xxx.md，然后：
1. 先不要写代码，告诉我你的实现计划
2. 我确认后再开始
3. spec 没覆盖的决策点先问我，不要自行决定
4. 实现完列出修改了哪些文件
```

## 6. README 模板

**何时写**：MVP 跑通、准备推到 GitHub（尤其开源）时。README 是产品的门面，不是开发笔记。

**写法原则**：

- 顺序固定：**logo → 名称 → slogan → 理念 → 功能 → 技术栈 → 本地复现 → 项目结构 → 安全 → 许可**
- logo 放 `assets/logo.svg`，居中，72×72
- 技术实现只写一段简介，**详细逻辑放 TECH.md**，README 里给链接
- **不含个人信息**：密钥、服务器路径、IP、部署细节一律不出现
- 本地复现要具体到命令可复制执行，最低限度列出必填的环境变量名（值留空）

## 7. 常见坑

1. **AI 改完不验证** — 永远 `git diff` 看实际改了什么
2. **AI 会过度设计** — 明确说"只改这一处，不要重构"
3. **AI 会遗忘** — 长对话后早期约定会忘，靠 AGENT.md 维持
4. **没备份就改数据库 schema** — 先 `.backup` 再 ALTER
5. **PM2 重启不读新 .env** — 必须 `pm2 restart xxx --update-env`
6. **SSH 默认 22 端口被暴力扫描** — 上线第一天改端口 + 禁密码登录
7. **Cookie 跨端口不共享** — 前后端分端口时要么反代要么改 Bearer Token
8. **SQLite 并发写会锁表** — 读多写少才用，否则 PG/MySQL
9. **前端单文件 > 100KB** — 开启 Nginx gzip
